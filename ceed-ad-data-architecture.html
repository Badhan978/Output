全体図

左から右へ「入力経路(外部) → 取込・処理(Cloudflare Workers) → データ(Cloudflare D1・23テーブル) → 画面(Cloudflare Pages・15) → 出力」。D1の各カードは主要列のみ抜粋(全列は data-model.md 正典)。太い3本の色線が主要フロー。Meta のリードは Webhook(即時)+ 10分Cron(取りこぼし補完)、日次数値は1時間Cronに分離。LPフォームは Vercel form-endpoint → Workers Webhook 直接POST。

方針

正の置き場は D1 のみ — Slack・代理店シートは入力経路であり、必ず D1 へ upsert してから画面が読む(直接参照しない)
実体行は ULID(TEXT)主キー。products / targets のみ固定列挙の自然キー(K1 等)をそのまま主キーにする
日時は UTC の ISO8601、金額は円の INTEGER、率(CTR/CPA/CVR 等)は保存せず毎回算出
物理削除はせず archived_at で soft delete。読み取りは基本 archived_at IS NULL
Meta/Google/代理店シート由来の行は source + external_id で UNIQUE、冪等 upsert で二重登録を防ぐ
判定は fail-closed — judgments は追記のみの履歴。未取得(行なし)と実測ゼロ(0)を区別する

裁定済み4 + 保留1

GitHub Issue #1 (駿冴さん裁定 2026-09-14) で5項とも推奨案どおり確定。条件・補足は data-model.md に反映済み。CPA の合格ラインのみ別件で保留。
1
judgments を保存するか、毎回算出するか
確定: 保存(履歴として追記) — Kill/合格は予算という不可逆な判断のトリガーで、後から実測値を追えないと事故追跡ができない。判定時点の実測値スナップショット列を追加
2
月次締めの繰越を行の更新にするか、別テーブルにするか
確定: leads.month_key を書き換える行更新 + carried_from_month に元月(直前の月のみ)を記録。2回目以降の繰越は activities(kind=carry_over)で補完
3
代理店シート取込を leads に直接 upsert するか、staging を挟むか
確定: staging は挟まず source+external_id で冪等 upsert。失敗行数・理由を sync_jobs.detail に記録し、失敗時は Slack「同期失敗」を通知
4
見出しの差し替えを新しい ads 行にするか、同一行の更新にするか
確定: 新規行(cycle_no を+1、旧行は archived_at)。cycle_no の採番単位は headline_code ごと
5
媒体ごとに ads 行を分けるか、見出し単位で1行に畳むか(モックとの相違点)
確定: 媒体ごとに分ける。画面は headline_code で GROUP BY 集約、片媒体のみの見出しは「—」表示
?
合格ラインの CPA は ¥6,000(目標CPA)か ¥10,000(即時差し替え線と同じ)か
保留(今は決めない) — モックの判定定数 productClearCpaIF: 6000 は据え置き。data-model.md §8 / kpi.md §5 参照
