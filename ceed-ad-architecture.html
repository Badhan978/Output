全体地図

左から右へ「媒体・流入 → 外部サービス → 取込・同期/認証・権限 → Cloudflare D1(全テーブル1枠) → 画面7群(56画面) → 通知・出力」。Cloudflare D1 は表名の列挙のみで、画面群への線はこの枠自体に対して引く。太い3本の色線が主要フロー。

主要な流れ 3本

① リード　Meta広告/自社フォーム → Meta同期・APIルート → leads → リード一覧 → 統合架電リスト → KPI・Slack通知
② 数値・判定　Meta Marketing API → Meta同期 → daily_metrics → 配信ダッシュボード → 判定4段 → 仮説台帳 → 次サイクル
③ 素材　見出し AB 管理・入稿(PAUSED作成) → assets → 素材ボード → decisions(判断) → 勝ちパターン → 次サイクル

壊れ方の設計

取得不全を空配列にしない — ページングは fail-open/fail-closed を名前で区別し、集計に使う経路は例外を投げる側を通す
マイグレーション未適用でも画面を落とさない — テーブル不在エラーだけ捕まえて「効いていない」と断り、列不足は1回だけ縮退リトライ
0 と「—」を区別する — 受注データが未取得・失敗のときは 0 でなく「—」を出す
判定できない時は集計を止める(fail-closed) — 区分が一意に定まらなければ「安全に表示できません」で停止し、取得失敗(赤)とは色も文言も分ける
RLS拒否は戻り値で検知する — DELETE拒否は「0行削除・エラー無し」で返るため、戻り行数を見ないと無音の嘘になる
