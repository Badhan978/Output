DATA FLOW ARCHITECTURE

データフロー全体図 —
画面・生成・投稿・実績がどこを通るか

リクエストの登録から、素材の生成・検品・実機投稿・実績回収までのデータの流れを1枚で示します。

対象：TikTok 運用自動化基盤

1🗺️システム全体のデータフロー

線の色は用途を表します。青＝画面まわりの通信、マゼンタ＝台帳の読み書き、アンバー＝ファイル、紫＝生成API、ティール＝実機操作、緑＝実績回収。

図1 ／ 4層構成でみるリクエストから投稿・実績回収までの一周
画面まわりの通信 台帳の読み書き ファイル 生成API 実機操作（adb） 実績回収
自社設備貴社オフィスに置く機材 Google貴社アカウントで所有 外部API従量課金の外部サービス
両端に矢印がある線は双方向（読み取りと書き込みの両方が走る）を意味します。 Apps Script と Claude Code は互いに直接つながらず、やり取りは必ずデータ層を経由します。 これにより、片方が停止しても状態は失われません。
画面が担うのは依頼と確認までです。実際の生成と投稿は Claude Code が後から実行するため、 画面の操作と実行は同時には起きません。

2🔢フローの説明 — ①〜⑥

図1の番号と対応しています。左上のリクエストから始まり、最後に実績がデータ層へ戻って一周します。

1リクエストの登録

担当者が画面から生成リクエストを送信。Apps Script が受けて スプレッドシートへ記録します。 フロント → バック → データ層

2素材の生成

Claude Code が未処理のリクエストを見つけてスキルを起動。 fal.ai を呼んで画像・動画をつくり、投稿用に組み立てます。 バック ⇄ 外部API

3保存と記録

できた素材を Drive へ保存し、その場所と状態を スプレッドシートへ書き戻します。 バック → データ層

4検品・承認

検品画面が台帳の状態と Drive のプレビューを表示。 Go なら投稿へ、差し戻しなら②へ戻って作り直します。 データ層 → バック → フロント

5実機投稿

同じ Claude Code が投稿スキルを起動。素材を端末へ送り、 実機スマホの TikTokアプリを adb で操作して投稿します。 データ層 → バック → 配信先

6実績の回収

投稿後の数値を実機の画面から取得して台帳へ戻します。 担当者は画面から実績を閲覧できます。 配信先 → データ層 → フロント

データフロー全体図 — TikTok 運用自動化基盤
図1は フロントエンド／バックエンド／データ層／外部サービス の4層構成。番号は「フローの説明」の①〜⑥と対応しています。
